# Targeted dependency remediation — October 13, 2026

This follow-up records implementation after the candidate review in [the advisory disposition](tooling-advisory-disposition-2026-10-13.md). The changes were subsequently approved and published through `62d773c`, with all PR checks passing. No signed-build or launch acceptance is implied.

## PostCSS selector parser

Applied exact **7.1.6** child overrides only beneath the existing `tailwindcss` and `postcss-nested@6.2.0` consumers. Their parent versions and the NativeWind/Expo stack remain unchanged. npm rejects an exact-version override selector for the directly declared Tailwind dependency when it differs from that declaration's range; the parent-name scope preserves the declared Tailwind 3 range instead. The lockfile contains the two expected nested parser copies and no unrelated upgrade.

`test:parser-override` is included in CI. Its four tests verify both consumer resolutions, escaped/Hebrew/RTL/nested selector handling, the actual PostCSS → Tailwind → NativeWind native-style path, and parsing 100,000 flat classes in a separate process with a 256 MiB heap and five-second deadline. The hostile-input check passed in about 118 ms locally, including child startup; this is regression evidence, not a performance guarantee.

With the real override installed in the isolated QA checkout, complete repository CSS was byte-identical to the old-parser baseline for web (42,135 bytes) and iOS mode (34,872 bytes). Conversion through installed `react-native-css-interop` was also deeply equal: 405 web-mode and 407 iOS-mode style-rule entries. These comparisons cover the repository's current styles, not arbitrary future styles or physical-device appearance.

Unsigned native generation with the candidate dependency set used the public `expo-template-bare-minimum@57.0.30` template, offline, `--no-install`, and no private credentials. Both platforms generated successfully. The existing `expo-system-ui` user-interface-style warning occurred in both baseline and candidate; it is not claimed fixed. Native compilation, CocoaPods resolution, signing and device acceptance remain separate gates.

## UUID used by native project generation

Applied exact **11.1.1** only beneath `xcode@3.0.1`; no Expo, xcode or React Native version change. This preserves the CommonJS `uuid.v4()` API used by the installed native-project generator. `test:uuid-override` is included in CI: it checks the resolved package, generates 1,000 identifiers alongside existing IDs, and verifies that the patched v3/v5/v6 methods reject undersized output buffers.

The generated Xcode project passed parse → write → parse equality. All 38 references to its 32 objects resolved; adding a synthetic resource in memory produced 35 objects with 41 resolving references. Its baseline/candidate serialized files matched after normalizing random UUIDs. The other **24 iOS files** and all **42 Android files** were byte-identical. The first resource-add probe assumed a named Resources group absent from Expo's template; the probe was corrected to create that group first. No app/native-source fix was needed, and no generated files were committed.

The final lockfile passed a clean offline install with lifecycle scripts disabled. The fresh npm audit is now **59 affected package entries: 54 high, five moderate, zero critical**, down from 73 before these overrides. The parser and UUID advisories no longer appear; braces, node-forge and sprintf-js remain open. Audit still exits nonzero. Neither reduced counts nor passing unsigned generation constitutes signed-build or launch acceptance.

## Remaining tooling controls and residual risk

CI now uses `npm ci --ignore-scripts`, matching the clean installation used for the successful full local checks. This prevents dependency lifecycle hooks during the CI installation step; application tests, Babel/Metro/Tailwind configuration and other invoked dependency code still execute. It does not remediate a parser vulnerability, validate a package's contents, change hosted EAS installation behavior or isolate signing secrets. Existing read-only workflow permissions and the 15-minute CI job deadline remain unchanged. No provider security/access setting was changed.

- **Trusted input / braces:** the inspected Tailwind globs are static repository configuration. A PR can still alter configuration and executable code. Keep unreviewed builds away from production/signing credentials, and do not add a request-facing glob service. The existing job deadline limits duration, not stack exhaustion. There is no verified patched release; broad package replacement or a new parser wrapper without coverage at the real transitive callers would not establish remediation. A supported depth-bound fix/backport and caller tests remain needed.
- **Precision / sprintf-js:** the inspected argparse/js-yaml help/error formats are authored constants. Keep user values as arguments, never format strings. Do not suppress an exception and claim a successful build. A generic wrapper elsewhere in this app would not protect argparse's direct calls, and replacing its grammar or imposing a precision policy inside the transitive package is not a demonstrated compatibility fix. A supported removal/patch or reviewed bound at those actual callers remains open. The local hostile-format probe confirms the package failure, not a network exploit in this application.
- **Signing chain / Forge:** leave certificate/signature verification enabled. No key, private certificate, trust root, provisioning profile, Apple account or hosted EAS signer was accessed or changed. Locally selected certificate/key provenance, every certificate/CSR input boundary, actual release-builder package versions and malformed-signature behavior still require review before this finding can be resolved or considered for explicit risk acceptance. The helper's Expo manifest-signing role is distinct from Apple binary signing. No homegrown cryptographic patch, forged certificate test against a service, or verification bypass was introduced.

These are bounded controls and unresolved findings, not risk acceptance on the owner's behalf. There is no verified safe in-range patched release for the three remaining root packages on the reviewed date.

## Further exposure review after publication

The remaining [braces](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm), [node-forge](https://github.com/advisories/GHSA-86w9-cpqp-85rv) and [sprintf-js](https://github.com/advisories/GHSA-hp3w-g68c-fv3c) advisories were re-read on October 13; each still lists no patched version. Installed direct caller paths were checked again against the lockfile and source. No additional small, validated fix was found, and package/lock files were not changed in this review.

- **braces:** Tailwind's content patterns remain authored repository constants; micromatch and chokidar still depend on braces. Replacing those patterns would not remove their parsers or protect PR-controlled configuration. An app-level glob wrapper would not intercept these actual tooling calls. Existing CI uses lifecycle-disabled installation, a read-only token and a 15-minute deadline; these reduce some exposure but do not fix recursion or attest to hosted builders.
- **sprintf-js:** The remaining chain is Babel/Jest coverage tooling → `@istanbuljs/load-nyc-config@1.1.0` → `js-yaml@3.15.2` → `argparse@1.0.10` → `sprintf-js@1.0.3`. Public registry metadata confirms latest load-nyc-config is still 1.1.0 and requires `js-yaml ^3.13.1`; no supported in-range parent update removes this chain. The loader calls YAML `load`; sprintf use is in argparse's authored help/error formats. A forced YAML major or custom formatter replacement would require separate compatibility validation and is not applied merely to reduce the count. No hosted request-to-format-string path was found in the inspected application.
- **node-forge:** Its Expo CLI/certificate helper call paths remain. Disabling AI does not remove a build/signature-verification dependency. No private key or certificate was inspected, no cryptographic verifier was patched, and no signature check was disabled. Actual release-builder versions, input provenance and supported remediation remain necessary evidence.

The unsigned native compilation preflight did not close compatibility acceptance: generated iOS Pods/workspace are absent, and an offline Android source-compile attempt stopped at Gradle's socket startup under explicit network containment, before compilation. Existing SDK/cache metadata alone is not a successful build. No dependency download, signing access, permissions change or hosted build was performed. The last audit count remains the previously recorded 59 entries; this follow-up is not a new audit run or risk waiver.
